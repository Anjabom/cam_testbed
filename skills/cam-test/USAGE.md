# cam-test 스킬 — 자세한 사용 설명

> 이 문서는 **사람이 읽는 안내서**다. Claude 가 따르는 절차서는 [SKILL.md](SKILL.md),
> 새 워크스페이스를 붙이는 절차는 [attach.md](attach.md) 에 따로 있다.

## 0. 이 스킬이 무엇을 대신해 주는가

시험할 워크스페이스에서 **말로** 시킨다.

```
~/black_ws$ claude
> 이 워크스페이스를 /home/me/video/night_a.mp4 로 테스트해줘
> 정지선 접근 구간(300~1200프레임)만 보고 싶어
```

스킬이 계약 확인 → 점검 → 실행 → **결과를 이 워크스페이스로 내보내기** → 결과 해석까지
순서대로 밟는다. 디버그 영상도 자동으로 딸려 온다.

**대신해 주지 못하는 것도 분명히 하자.** 스킬은 ROS 2 · GPU 드라이버 · 학습 가중치 ·
cam_testbed 자체를 설치해 주지 못한다. 그것들이 없으면 "없다"고 말하고 멈춘다.

### ★합격/불합격은 안 찍는다★ (2026-09 개편)

예전에는 시나리오 YAML 에 `checks:` 를 써서 임계값으로 판정했다. 리포트 맨 위에
「13/13 통과」가 찍혔다. 그걸 없앴다. 이유는 둘이다.

1. **그 숫자의 근거가 없었다.** 대부분 "첫 런에서 이 값이 나왔으니 이걸 기준으로"에서
   출발한 것이라, 실제로는 「지난번과 같은가」를 「좋은가」로 부르고 있었다.
2. **초록 한 줄이 나머지를 안 읽게 만들었다.** 행이 0 인 런도 「전부 통과」로 찍혔다
   — 위반할 것이 없으면 위반도 없기 때문이다.

지금 나오는 것은 **관측값과 그림뿐**이고, 판단은 그것을 읽는 사람(과 Claude)이 한다.
시나리오 파일도 없어졌다 — 영상 경로와 구간을 명령줄에 바로 준다.

## 1. 설치

### 1-1. 이 머신에 cam_testbed 가 있어야 한다

```bash
git clone https://github.com/Anjabom/cam_testbed.git ~/cam_testbed
cd ~/cam_testbed
cp local.yaml.example local.yaml
```

**`local.yaml` 의 가중치 경로를 이 머신에 맞게 고친다.** `.example` 에 적힌 것은 남의
머신 경로다. 안 고치면 `doctor` 가 잡아낸다.

### 1-2. 플러그인으로 설치한다

```
/plugin marketplace add ~/cam_testbed          # 로컬에서 (또는 레포 URL)
/plugin install cam-test@cam-testbed
```

**왜 프로젝트 스킬(`.claude/skills/`)이 아니라 플러그인인가** — 프로젝트 스킬은 그
디렉터리 안에서만 뜬다. 우리는 `~/black_ws` 에서 부르고 싶으니 플러그인이라야 한다.

### 1-3. 확인

```
> 카메라 인지 테스트베드 스킬 있어?
```

## 2. 첫 실행

```
~/black_ws$ claude
> 이 워크스페이스 /home/me/video/night_a.mp4 로 돌려줘. 차선이 잘 잡히는지 보고 싶어
```

스킬이 실제로 치는 명령은 이것이다 — 직접 쳐도 된다.

```bash
source /opt/ros/humble/setup.bash
cd ~/cam_testbed

python3 -m tb.run doctor --contract contracts/black_vote.yaml \
    --video /home/me/video/night_a.mp4

python3 -m tb.run run --contract contracts/black_vote.yaml \
    --video /home/me/video/night_a.mp4 \
    --start 300 --limit 900 \
    --note "차선이 잘 잡히는지" \
    --out ~/black_ws
```

**시나리오 파일도, 영상 등록도 없다.** 필요한 것은 계약 하나와 영상 경로다.

자주 쓰는 조합(영상·구간·파라미터)은 `presets/*.yaml` 로 두고 `--preset` 으로 부를 수
있다. 프리셋은 **재생 조건만** 담는다 — 판정 어휘는 들어가지 않는다. 명령줄 인자가
언제나 프리셋을 이긴다.

## 3. 결과는 어디에 남는가

```
~/black_ws/testbed_results/
├── INDEX.md                       ← 시험 이력 (런당 한 줄)
├── COLCON_IGNORE                  ← colcon 이 mp4 를 훑지 않게
└── 0905_002023_black_vote/
    ├── README.md                  ← ★이 폴더가 무엇인지 스스로 설명한다★
    ├── report.md                  ← 사람이 읽는 계측 요약
    ├── summary.json               ← 같은 내용, 기계용
    ├── signals.csv                ← 프레임별 원표
    ├── lane_debug.mp4             ← ★디버그 영상★
    ├── params_actual.yaml         ← 노드가 실제로 들고 돈 값 전부
    └── run_env.json               ← 호스트·GPU·가중치·코드 해시
```

원본(`raw.jsonl` 포함)은 `~/cam_testbed/runs/<런>/` 에 그대로 남는다. 계약을 고쳐
다시 읽거나(`reanalyze`) 디버그 영상을 다시 잡는 것(`replay`)은 원본으로 하고,
새 산출물이 생기면 **다시 내보내면 된다**(덮어쓴다).

### `run_env.json` 을 왜 넣었는가

결과가 워크스페이스에 들어가면 남의 머신 숫자와 한자리에 섞인다. 몇 달 뒤 "왜 값이
다르지"를 물을 때 답할 수 있어야 한다 — 호스트·GPU·가중치 경로·대상 코드 해시가
거기 있다. **GPU·가중치·영상이 다르면 숫자는 비교할 수 없다.**

## 4. 결과를 읽는 순서 — 지켜야 한다

### ① 「행 N」을 맨 먼저 본다

```
- 투입 프레임 900 → 출력 행 0 (유실 1.000)
```

행이 0 이면 그 아래 모든 표는 빈 입력에서 나온 것이다. 리포트가 그 경우 맨 위에
경고를 박고, 내보내기도 「잰 것이 없다」고 말한다. 원인은 보통 노드가 뜨다 죽은
것이다 — `runs/<런>/<노드>.log` 를 본다.

### ② 「계약 정합」을 본다

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `❌ 불일치` | 메시지는 왔는데 선언한 경로가 하나도 안 맞았다 | **계약의 그 `path:` 한 줄**을 고치고 `reanalyze` |
| `🔁 대체경로` | 두 번째 이후 후보로 잡혔다 | 정상(마이그레이션 중) |
| `· 미수신` | 그 토픽에 메시지가 한 번도 안 왔다 | 발행 조건이 안 맞았을 수 있다 |

**여기가 빨간데 숫자를 논하면 안 된다.** 잰 자리가 틀린 것이다.

### ③ 「받는 쪽 게이트 통과율」

이 리포트에서 가장 쓸모 있는 표다. 「차선을 봤나」가 아니라 **받는 쪽 노드가 실제로
그 프레임을 썼나**를 잰다.

```
**실질 기여율 18.3%** (11 / 60 프레임) · 최대 병목: **conf 임계값**
```

인지가 아무리 좋아도 받는 쪽 게이트를 못 넘으면 주행에는 한 프레임도 기여하지 않는다.
**최대 병목 단계가 곧 다음에 손댈 곳이다.**

### ④ 신호 통계 · 단계 전이 · 노드 로그 · 디버그 영상

숫자가 이상하면 **디버그 영상**을 본다. 그때 노드가 무엇을 보고 그 값을 냈는지
확인할 유일한 그림이다.

## 5. 고치고 다시 돌리는 고리

```bash
# ① 대상 코드를 고친다 (파이썬만 고쳤으면 빌드 불필요 — --symlink-install)
python3 -m tb.run build --contract contracts/black_vote.yaml   # 필요할 때만

# ② 같은 조건으로 다시 돌린다
python3 -m tb.run run --contract … --video … --start 300 --limit 900 \
    --note "conf 게이트 손본 뒤" --out ~/black_ws

# ③ 전후를 나란히
python3 -m tb.run diff runs/<이전런> runs/<이번런>
```

`diff` 는 **판정하지 않는다.** 신호별 평균/p95/최대 차이만 낸다. 두 런의 조건(영상·
구간·파라미터·기하)이 다르면 표 위에 경고가 붙는다 — 그때는 숫자를 비교하지 말고
조건을 먼저 맞춘다.

## 6. 카메라 보정은 웹앱에서

IPM 사각형·ROI·픽셀↔미터·BEV 기준선은 **보면서 맞춰야** 하는 값이다.

```bash
cd ~/cam_testbed && python3 -m tb.run app     # 별도 창 (또는 web — 브라우저)
```

- 영상이든 **사진 한 장**이든 경로만 고르면 열린다(등록 절차 없음)
- 화면의 BEV 는 대상 노드가 만드는 것과 **같은 변환**으로 그려진다
- 체스보드 사진으로 **K/D 를 실측**할 수 있다
- 맞춘 값은 `local.yaml` 에 저장되고, 워크스페이스로 **내보내기**가 따로 있다
- 「노드와 대조」가 내가 그리는 BEV 와 노드의 실제 BEV 를 맞춰 본다

자세한 것은 웹앱의 «사용 안내» 탭에 있다.

## 7. ★절대 하지 않는 것★

### 임계값을 지어내지 않는다

이 도구는 판정하지 않는다. "이 정도면 됐다"는 기준이 필요하면 **근거를 먼저 말하고
확인받는다.** 지어낸 숫자는 이후 모든 비교의 잣대가 된다.

### 재는 쪽을 고쳐 숫자를 좋게 만들지 않는다

계약의 `path:`·게이트 상수를 고치는 것은 「잰 자리가 틀렸을 때」뿐이다. 실차 백엔드
(`.engine`)를 `.pt` 로 낮춰 통과시키는 것도 같은 금지다 — 재는 대상 자체가 달라진다.

### `tb/*.py` 와 `web/*` 에 대상 워크스페이스의 이름을 쓰지 않는다

토픽명·필드 배치·노드명·파라미터명은 전부 계약 YAML 에만 있다. 워크스페이스가 하나
늘면 **계약 파일이 하나 느는 것**이지 코드가 바뀌는 것이 아니다.

### 외부 의존성을 추가하지 않는다

웹앱은 표준 라이브러리만 쓴다(CDN·웹폰트·JS 라이브러리 없음). 대회 현장에 네트워크가
없어도 돌아야 한다.

## 8. 함정 모음 (데인 것들)

| 함정 | 무엇이 일어나나 |
|---|---|
| **행 0 인데 표는 멀쩡** | 노드가 죽어도 리포트는 나온다. 행부터 본다 |
| **`.pt` 로 재기** | 지연·마스크가 실차와 달라지는데 표는 그대로다. 계약의 `require_params` 가 막는다 |
| **결과를 머신 넘어 비교** | GPU·가중치가 다르면 값이 다르다. `run_env.json` 을 대조한다 |
| **`mp4v` 코덱** | 브라우저가 오류 없이 검은 화면만 띄운다. `tb/encode.py` 를 거치면 H.264 다 |
| **`lockstep` 으로 타이밍 판단** | 벽시계가 실제로 흐른다. 타이밍은 `--mode realtime` 으로 본다 |
| **디버그 영상 없이 지나감** | 사후에 만들 수 없다. `replay` 로 같은 조건에서 다시 잡는 수밖에 없다 |
